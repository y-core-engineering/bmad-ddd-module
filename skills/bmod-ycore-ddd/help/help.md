# ycore-ddd knowledge

This document covers the skills of the `ycore-ddd` module: what each one gives the user, when to recommend it, and what to offer next.

## The skills

- `ycore-ddd-big-picture`: prepares a Big-Picture Event Storming in an interview about the product idea, then facilitates it with a team of agents over up to six rounds, ending in `context-map.md`, `ubiquitous-language.md` and `event-storming.md` in the domain model folder; a run resumes in a new session from its files. Recommend it as soon as an idea description, a product brief or a PRFAQ exists, before `bmad-spec` (and before `bmad-prd` when one is needed), or when the user wants to find Bounded Contexts, a Context Map or a glossary. A brief from `bmad-product-brief` or `bmad-forge-idea` sharpens its interview but is not required; the skill reads the idea itself and asks about the rest. Afterwards offer `ycore-ddd-design-level`, and `bmad-spec` with the three artifacts as input; `bmad-prd` first when requirements need real detail.
- `ycore-ddd-design-level`: builds a catalog of the Bounded Contexts from the Big Picture in an interview (full team run or lean note, order by risk, constraints), then runs a Design-Level Event Storming per context with a team of agents: Commands with permissions, Aggregates with invariants, Policies, Read Models, ACLs and abuse cases, ending in `<bc-id>-<name>/design.md` in the domain model folder. Recommend it after `ycore-ddd-big-picture`, or when the user wants to design the Aggregates or find the invariants of a context. Afterwards offer the next context in the catalog, then `bmad-spec` with the design files; `bmad-architecture` first when separately built parts must fit, asking it for a `Context`/`Path` table that the model check reads. `ycore-ddd-model-check` once code exists.
- `ycore-ddd-model-check`: checks the code against the domain model (glossary, Context Map, Design-Level per Bounded Context, invariants) in five checks and writes a report whose findings each name a code location and a model counterpart. It fixes nothing, and it needs the domain model that `ycore-ddd-big-picture` and `ycore-ddd-design-level` produce; without it every check ends as not checked. Recommend it after `bmad-build` or `bmad-retrospective` finishes an epic, before planning the next one, and whenever the user asks whether the code still matches the model. With the user it then decides every high and medium finding: fix in code (`bmad-build`), update the model (`ycore-ddd-design-level` or `ycore-ddd-big-picture`), or accept the deviation, recorded in `accepted-deviations.md` so later checks do not report it again. Scope comes from the epic's build plans (`baseline_revision`) or a commit range, and files are assigned to contexts through `code-map.md` when it exists. Asked to "bind the model check to the retrospective" (best right after setup), it writes a team override for `bmad-retrospective` through `bmad-customize`, so every retrospective reads the report and does not accept an epic with an undecided high finding.

## How the skills work

Like BMad's own planning skills, the two Event Storming skills know three intents: create, update (a revision round on a named part) and validate (a review report that changes nothing). They offer a Coaching path, the full interview with a pause after every round in which the round's Hotspots are put to the user, and a Fast path that drafts the brief or catalog with `[ASSUMPTION]` tags and then runs the rounds, the draft artifacts and the reviewer gate without a halt up to one final acceptance (per context in the Design-Level); every assumption and every Hotspot is decided there, so the Fast path skips pauses, never a decision. Hotspots are asked through Claude's question tool where available. Both workshops scale their depth to the stakes (hobby, internal, launch), read the project and environment before asking, and put only domain questions to the user; technical details pass on under `Open for spec`. Before handover a reviewer gate runs independent reviewer subagents (lenses set in `workflow.finalize_reviewers`). Decisions are kept in memlogs in the domain model folder, so a run continues in a new session. Headless, the workshops run up to the first point that needs the user and stop there; the model check runs completely, which suits unattended build loops.

## Where things land

All three skills keep the domain model in `modules.ycore-ddd.domain_model_folder`; the check writes its reports to `modules.ycore-ddd.review_folder`; `bmad setup ycore-ddd` shows and changes the answers.
